# Требования к безопасности
1. Коммуникация должна быть осуществлена по защищенным каналам связи с использованием шифрования (TLS, SSL)
2. Конфиденциальные и секретные данные не должны передаваться. Кроме случаев с наличием веских оснований и с применением строгих мер защиты (например, шифрования на уровне payload и аудитируемого доступа)
3. Система должна быть защищена от наиболее распространённых типов атак на каналы связи и сессии (MITM, ID Spoofing, Information Harvesting, Session Hijacking и др.)
4. Должны быть настроены аутентификация и авторизация
5. Доступ администраторов к конфиденциальным данным должен быть строго регламентирован, зафиксирован и протоколироваться (audit logging). Желательно использование подхода zero-knowledge
6. Доступы пользователям должны соответствовать принципу наименьших привилегий (Least Privilege access)
7. ID пользователей не должны быть указаны явно и должны быть зашифрованы
8. Платформа должна поддерживать аудит доступа и действий пользователей и администраторов

# Протоколы аутентификации и авторизации

Протоколы авторизации и аутентификации должны быть реализованы на основе токенов без передачи учетных данных пользователя. В качестве протокола предлагается использовать OpenID Connect в связке с OAuth 2.0 для авторизации.
Необходимо использовать короткоживущие access-токены и механизмы обновления токенов (refresh tokens) с минимальным временем жизни.
Access-токены должны быть подписаны и проверяемы (например, JWT с подписью HMAC или RSA).
При передачи данных между системами необходимо убедиться, что запрос происходит от авторизованного источника

# Взаимодействие между системой предприятия и внешними платформами

Мобильное приложение выполняет роль клиента, инициирующего запрос к внешней платформе через защищённый API-шлюз предприятия. Аутентификация пользователя к внешней платформе происходит с использованием OIDC через Single Sign-On (SSO). После успешной аутентификации внешний провайдер выдаёт access-token, ограниченный по времени и доступу (по принципу наименьших привилегий). Все последующие взаимодействия выполняются через backend предприятия или шлюз — не напрямую с устройства пользователя.
Также предполагается использование API Gateway, который будет контролировать все входящие и исходящие запросы, авторизацию и журналировать действия.
